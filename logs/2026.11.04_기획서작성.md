## 2. 아이디어 제안
 
### 👤 요청
- 교수님 출장이 잦아 강의를 혼자 듣는 학생을 위한 서비스 아이디어 제시
- 소프트웨어학부 학생만 인증 후 사용
- 출장으로 인한 휴강, 과제 제출일, 교수님 공지사항을 **다 같이 등록·수정**하고 **댓글로 의견을 공유**하는 공유 캘린더
### 🤖 응답
- "혼자 수강하는 학생의 정보 격차"라는 구체적인 문제가 있어 대회 취지에 잘 맞는다고 평가
- **독창성 보완:** 심사에서 "단톡방이나 LMS로 되지 않나요?" 질문에 대비해 기존 수단과의 비교표 작성
  | 기존 수단 | 한계 | 이 서비스 |
  |---|---|---|
  | LMS 공지 | 교수님이 올려야만 있음, 구두 공지 누락 | 학생들이 함께 채움 |
  | 과 단톡방 | 정보가 대화에 묻힘, 아는 사람 없으면 접근 불가 | 과목별 캘린더로 구조화 |
  | 에브리타임 | 익명, 인증 범위 넓음, 일정 형태 아님 | 학부 인증 + 일정 중심 |
  | 구글 공유캘린더 | 인증 없음, 과목별 관리·의견 공유 어려움 | 과목 구독 + 댓글 |
- **핵심 리스크: 정보 신뢰도.** 누구나 등록·수정하면 잘못된 정보가 가장 큰 약점이 되므로 다음을 제안
  - 출처 첨부 (공지 캡처, LMS 링크, 구두 공지 등)
  - "나도 확인했어요" 버튼으로 신뢰도 배지
  - 수정 이력 및 되돌리기
  - 신고 기능
- **인증 방식 선택지:** 학교 이메일만으로는 소속 학부 확인이 안 될 수 있음 → 이메일 + 학번 규칙 / 이메일 + 학생회 초대 코드 / 학생증 사진 + 관리자 승인 비교
- **MVP 범위:** 가입·로그인, 과목 구독, 일정 등록·수정·삭제, 월간·주간 캘린더, 댓글. 여유 시 D-1 알림, 신뢰도 버튼, .ics 내보내기
- **기술 스택 예시:** Next.js + Supabase(이메일 OTP 인증, DB, 실시간) + FullCalendar
### ✅ 결정
- 주제 확정: 소프트웨어학부 학생 전용 과목별 공유 캘린더

1. **신뢰도:** 출처 첨부, 좋아요로 신뢰도 표시, 관리자에게 신고하는 기능 도입

   3. 메인 화면: 월간·주간 캘린더, 우측 상단 일정 등록 버튼, 공지 유형별 색상 구분
   4. 공지 클릭(터치) 시 상세 페이지 이동 (구글 캘린더 형식 참고)

4. 여유가 있으면 구글 캘린더 내보내기
5. **AI 활용 계획:** 기획, 구현, 디버깅·리뷰 모두 Claude. 기술 스택별 장점 정리 요청

- **학번 인증의 빈틈:** 학번 규칙은 정규식으로 검사 가능하지만, 학교 이메일 아이디가 학번이 아니면 타 학부 학생이 이메일 인증 후 소프트웨어학부 학번을 지어 입력해도 막을 수 없음
- **"전부 Claude"의 보완:** 중간 심사 최대 비중(40%)이 도구 선정·파이프라인 설계이므로, 같은 Claude라도 단계별 쓰는 방식을 달리해야 함 (채팅으로 기획, Claude Code로 구현, 별도 세션으로 리뷰해 자기 코드 채점 방지)
- **기술 스택 비교**
  | 영역 | 선택지 | 비교 요점 |
  |---|---|---|
  | 프론트 | Next.js | AI가 잘 짜는 조합, 화면과 API를 한 프로젝트에서 처리, Vercel 배포 쉬움 |

  | | Flutter | 앱 배포 가능하지만 빌드·테스트 번거로움 |
  | 백엔드 | Supabase | 이메일 인증, PostgreSQL(관계형 데이터에 적합), RLS 권한, 실시간 기능 |
  | | Firebase | NoSQL이라 관계형 조회가 번거로움 |
  | | 직접 구축 | 통제력은 높지만 대회 기간에 부담 |
  | 기타 | FullCalendar, Tailwind, Vercel, .ics | 캘린더 UI, 스타일, 배포, 내보내기 |
- 반응형 웹 + PWA로 앱 없이도 모바일에서 앱처럼 사용 가능
- 추천 조합: Next.js + Supabase + FullCalendar + Tailwind + Vercel
- "누적 설명" 기능은 일정(event)과 설명 기여(contribution) 테이블을 분리해야 출처별 신뢰도와 수정 이력을 보여줄 수 있다고 제안

## 4. 2차 결정 (인증 방식 변경)
 
### 👤 요청
1. **인증 변경:** 이메일 인증 없이 학번 + 비밀번호로만 가입. 학교에서 학년별 학번 명단을 받아 중복 검사
2. **AI 파이프라인:** 기획·구현·디버깅은 Claude, 리뷰·테스트는 Claude + Gemini Pro로 2중 검증
3. **프론트:** React + Vercel, 반응형 웹 + PWA
4. **백엔드:** Supabase
5. FullCalendar, Tailwind CSS 사용. 구글 캘린더 내보내기 방식은 MVP 완료 후 결정
6. **누적 설명 기능 제외:** 첫 등록자만 공지명·상세 설명 작성, 나머지 정보는 사용자들이 댓글로 등록
### 🤖 응답
- **학번 + 비밀번호 방식의 한계**
  - 명의 도용: 명단 대조로 없는 학번은 막지만, 타인의 학번을 아는 사람이 먼저 가입하는 것은 못 막음 → 관리자 문의 경로 필요
  - 명단 확보: 학번 명단은 개인정보라 제공받지 못할 수 있음 → 프로토타입은 더미 명단으로 시연하는 대비책
  - 비밀번호 분실: 이메일이 없으면 재설정 메일을 보낼 수 없음
  - 구현 팁: 학번을 가상 이메일로 바꿔 Supabase 인증에 넣는 방법
- **서버 로직 위치:** React(Vite)는 브라우저에서만 동작하므로, 명단 대조를 브라우저에서 하면 명단 전체가 노출됨 → Supabase Edge Function 등 서버에서 처리하고 명단 테이블은 RLS로 차단
- **첫 등록자만 수정 가능할 때의 문제**
  - 틀린 정보가 고쳐지지 않음 → 댓글 좋아요 + 최다 좋아요 댓글 상단 고정, 관리자 신고
  - 중복 일정 → 등록 전 같은 과목·같은 날짜 기존 일정을 먼저 보여주기
- **교차 검증 기록:** 두 모델의 공통 지적, 단독 지적, 오탐을 기록하면 최종 발표 자료가 됨
- DB 테이블 초안 8개 제시

## 6. DB 컬럼 질문 및 전체 정리
 
### 👤 요청
1. 인증 구조 확정
2. `admission_year`는 왜 필요한지
3. `id`와 `student_id`의 차이
4. `created_at`은 왜 필요한지
5. 일정 유형(type)에 시험(test) 추가
6. `all_day`는 왜 필요한지
- SQL 파일은 중간 발표 때 만들지 않음. 기획안 작성 전 지금까지의 결정 사항 전체 정리 요청
### 🤖 응답
- **admission_year:** 학년 단위 명단 관리용으로 넣었지만 학번 앞 4자리로 계산 가능 → 삭제 권장
- **id vs student_id**
  - id: Supabase가 만드는 내부 고유 번호, 절대 안 바뀜, 다른 테이블이 사용자를 가리킬 때 사용
  - student_id: 사람이 입력하는 학번, 로그인·명단 대조용

## 7. 전과·복수전공 학생 처리 고민
 
### 👤 요청
- 학과에 전과·복수전공 학생이 많은 편인데 어떻게 필터링하는 게 좋을지 질문
### 🤖 응답
- 전과·복수전공생은 같은 과에 아는 사람이 적어 **이 서비스가 가장 필요한 사용자**이므로 걸러내기보다 제대로 받아들이는 방향 제안
- **학번 규칙의 문제:** 학번 학과 코드는 입학 당시 소속이라 실제와 어긋남
  | 학생 유형 | 학번 규칙 결과 | 바람직한 결과 |
  |---|---|---|
  | 소프트웨어학부 입학·재학 | 통과 | 통과 |
  | 타과 → 소프트웨어학부 전과 | 차단 | 통과 |
  | 소프트웨어학부 → 타과 전과 | 통과 | 차단 |
  | 타과 + 소프트웨어 복수전공 | 차단 | 통과 |
- **1순위:** 과사무실 명단(전과·복수전공 포함)을 기준으로 판단하고 명단에 학생 유형 기록
- **2순위(대비책):** 명단에 없는 학생은 증빙 첨부 후 관리자 승인, 계정은 승인 대기(pending) 상태
- 증빙 이미지는 처리 후 삭제, 학기마다 명단 갱신
- 부전공 포함 여부와 전과 시 학번 변경 여부 질문
### ✅ 결정
- 없음 (선택지 검토)
