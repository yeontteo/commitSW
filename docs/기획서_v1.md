# commitSW 중간보고서

### 소프트웨어학부 학생이 함께 만드는 과목별 공유 캘린더

GitHub : https://github.com/yeontteo/commitSW

---

## 1. 프로젝트 개요

| 항목     | 내용                                                          |
| ------ | ----------------------------------------------------------- |
| 서비스명   | commitSW                                                    |
| 컨셉     | 개발자가 코드 변경을 커밋하듯, 학생들이 휴강·과제·시험·공지를 캘린더에 "커밋"해 함께 기록하고 공유한다 |
| 한 줄 소개 | 혼자 들어도, 결석해도 공지는 놓치지 않는 소프트웨어학부 전용 공유 캘린더                   |
| 형태     | 반응형 웹 + PWA (PC·모바일 모두 사용, 홈 화면에 추가하면 앱처럼 실행)               |

## 2. 문제 정의

- 소프트웨어학부 특성상 교수님 출장으로 **휴강**이 잦고, 여러 과목의 **과제**가 한 시기에 몰려 일일이 챙기기 어려운 경우가 많다.
- 이런 변경 사항은 LMS에 올라오지 않고 **수업 중 구두 공지**나 **오픈채팅방으로만 전달**되는 경우가 많다.
- **그 결과 같은 수업에 아는 사람이 없는 학생이나 특정 날짜에 수업에 참여하지 않은 학생은 정보를 놓치기 쉽다.**
- 특히 **전과생**과 **복수전공생**은 학부 내 정보 네트워크가 부족하여 해당 문제를 더욱 심각하게 겪는 경향이 있다.

**목표 사용자:** 소프트웨어학부 본전공 재학생, 소프트웨어학부로 전과한 학생, 소프트웨어학부 복수전공 학생

## 3. 기존 서비스와의 차별점

| 기존 수단    | 한계                                    | commitSW                                 |
| -------- | ------------------------------------- | ---------------------------------------- |
| LMS 공지   | 교수님께서 직접 올리신 온라인 공지만 있음               | 학생들이 구두 공지까지 함께 채움                       |
| 수업 오픈채팅방 | 조교님이 수업에 직접 참관하지 않아 공지가 안 올라오는 경우가 많음 | 교수님 구두 공지+오픈채팅방 공지를 학생들이 함께 채워 정보력을 더 높임 |
| 에브리타임    | 인증 범위가 넓고 일정 형태가 아님                   | 학부생 인증 + 일정 중심                           |
| 구글 공유캘린더 | 학부생 인증, 과목별 관리, 신뢰도 장치가 없음            | 과목 구독 + 출처 첨부 + 좋아요·신고                   |

**핵심 차별점**

1. **소프트웨어학부생 전용 공지 공유:** 학부 명단 인증과 전과·복수전공 승인을 거친 소프트웨어학부 학생만, 구두·오픈채팅방 공지까지 함께 공유한다.
2. **신뢰도 장치:** 출처 첨부, 좋아요, 댓글 정정, 신고로 여러 학생이 같은 공지를 교차 확인하며 신뢰성을 높인다.
3. **과목 단위 구독:** 듣는 과목만 구독해, 여러 과목의 휴강·과제·시험을 한 캘린더에서 본다.

## 4. 기능 요구사항 (MVP)

| ID  | 기능       | 요구사항                                                                                                                                          |
| --- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| F1  | 회원가입·로그인 | 1. 학번 + 비밀번호 + 복구용 이메일로 가입. 본전공은 학번 규칙(20xx041xxx)과 학부 명단 대조, 중복 가입 차단.<br>2. 명단에 없는 전과·복수전공생은 증빙 사진 첨부 후 관리자 승인.<br>3. 복구용 이메일 인증 및 비밀번호 재설정 |
| F2  | 수강 과목 선택 | 1. 이번 학기 과목 중 수강 과목을 선택하면 해당 과목 일정만 표시                                                                                                        |
| F3  | 메인 캘린더   | 1. 월간/주간 전환<br>2. 유형(휴강/과제/시험/공지)별 색상 구분<br>3. 우측 상단 일정 등록 버튼<br>4. 종일 일정(휴강, 공지)과 시각 일정(과제, 시험) 구분                                           |
| F4  | 일정 등록    | 1. 과목, 유형, 제목, 설명, 출처(LMS/구두/이메일/기타 + 링크·캡처), 일시 입력 (과제, 시험은 시각까지).<br>2. 저장 직전 같은 과목·같은 날짜의 기존 일정을 보여줘 중복 방지.<br>3. 제목·설명은 첫 등록자만 작성·수정      |
| F5  | 일정 상세    | 1. 구글 캘린더 상세 화면 참고.<br>2. 과목, 유형, 제목, 설명, 출처, 작성자, 일정 좋아요 수(신뢰도) 표시.<br>3. 추가 정보·정정은 댓글로 등록<br>4. 댓글 좋아요 기능을 통해 최다 좋아요를 받은 댓글은 상단 노출          |

| F7  | 관리자      | 1. 전과·복수전공 승인/거절<br>2. 신고 처리(숨김, 사용자 정지)<br>3. 문의 처리                                                                                          |

*MVP 이후:* 구글 캘린더 내보내기

## 5. 사용자 시나리오

- **본전공 학생:** 가입 → 수강 과목 3개 선택 → 캘린더에서 다음 주 화요일 ㅇㅇ과목 "휴강" 확인 → 상세 페이지에서 LMS 출처와 좋아요 12개 확인 → 댓글의 보강 일정 확인
- **복수전공 학생:** 가입 시 명단에 없음 안내 → "복수전공" 선택 후 학적 화면 캡처 첨부 → 승인 대기 → 관리자 승인 후 이용
- **정보 등록자:** 수업 중 과제 마감 연기 구두 공지 → 유형 "과제", 출처 "구두 공지"로 등록 → 다른 학생들의 좋아요로 신뢰도 상승
- **틀린 정보 정정:** 잘못된 시험 장소 발견 → 댓글로 정정 + 관리자 신고 → 관리자가 숨김 또는 수정 요청

## 6. 데이터 설계 및 보안

**테이블 (11개):** student_roster(학부 명단) · profiles(회원, 학생 유형, 상태) · verification_requests(전과·복수전공 승인) · courses · enrollments(수강 과목) · events(일정) · comments · event_likes · comment_likes · reports(신고) · inquiries(문의)

**보안 및 개인정보 처리**

- 학번 명단 대조와 권한 검사는 **서버에서만** 실행 (브라우저에 명단 노출 금지)
- 행 단위 권한(RLS)으로 "본인 글만 수정", "관리자만 신고 조회" 등을 DB에서 강제
- 승인 대기 사용자는 캘린더 조회 불가
- 증빙 이미지는 관리자만 열람하고, 승인·거절 처리 후 삭제
- 다른 테이블에는 학번 대신 내부 고유 ID 저장

**알려진 한계**
- 타인의 학번으로 먼저 가입하는 명의 도용은 원천 차단이 어려워 관리자 문의로 대응한다.
- 정보의 정확성은 사용자 참여(출처, 좋아요, 댓글, 신고)에 의존한다.

## 7. AI 워크플로우 및 환경 설정

### 7-1. 개발 환경

| 영역        | 선택                       | 선택 이유                                                      |
| --------- | ------------------------ | ---------------------------------------------------------- |
| AI 코딩 도구  | Claude Code (VS Code 확장) | 프로젝트 파일을 직접 읽고 수정하며, CLAUDE.md로 맥락 유지                      |
| 프레임워크     | Next.js (React)          | 화면과 서버 로직(명단 대조, 가입 처리)을 한 프로젝트에서 처리                       |
| 스타일       | Tailwind CSS             | 반응형 화면을 빠르게 구현                                             |
| 캘린더 UI    | FullCalendar             | 월간/주간 전환, 유형별 색상, 종일 일정 기본 제공                              |
| 백엔드·DB·인증 | Supabase                 | 이메일 인증, 비밀번호 재설정, 파일 저장, RLS 기본 제공. 관계형 DB로 과목·일정·댓글 관계 처리 |
| 배포        | Vercel + GitHub          | GitHub에 푸시하면 자동 배포                                         |
| 교차 리뷰     | Claude + Gemini Pro      | 다른 모델의 시각으로 Claude 결과 검증                                   |

### 7-2. AI 개발 파이프라인

```
기획·요구사항 → CLAUDE.md → 설계안 → 승인 → 구현 → 교차 리뷰 → 배포
   (Claude)   (맥락 고정)  (Claude Code)(Claude Code)(Claude+Gemini)(Vercel)
                                       ↑         ↕         │
                                       │       디버깅       │
                                       │   (Claude Code)   │
                                       └───리뷰 지적 사항 ──┘
```

| 단계 | 도구 | 쓰는 방식 |
|---|---|---|
| 기획·요구사항 | Claude | 문제 정의, 기능 명세, DB 설계, 시나리오 정리 |
| 구현 | Claude Code | CLAUDE.md의 작업 규칙에 따라 기능 단위로 설계안을 받고, 승인 후 구현 |
| 디버깅 | Claude Code | 재현 순서, 에러 로그, 시도한 내용을 정리해 원인 분석 요청 |
| 리뷰·테스트 | Claude + Gemini Pro | 같은 코드·같은 프롬프트로 두 모델에게 각각 리뷰를 받아 교차 검증 |

**교차 검증 방식:** 두 모델이 모두 지적한 문제는 우선 수정하고, 한쪽만 지적한 문제는 직접 확인 후 판단한다. 오탐은 기록해 모델별 특성을 비교한다.

**맥락 관리:** 기획안의 결정 사항(기능 명세, 스택, DB 설계, 보안 규칙)과 작업 규칙을 프로젝트 루트의 `CLAUDE.md`에 정리한다. Claude Code가 매 작업마다 이 파일을 참고하므로 결정과 어긋난 코드를 줄일 수 있다. 결정이 바뀌면 `CLAUDE.md`부터 수정한다.

## 8. 초기 프롬프트 전략

### 8-1. 기본 원칙

1. **맥락 고정:** 프로젝트 결정 사항을 CLAUDE.md 한 곳에 두고 매 작업의 기준으로 삼는다.
2. **기능 단위 분할:** 한 번에 하나의 기능만 요청한다.
3. **설계 후 구현:** 코드를 바로 받지 않고 설계안을 먼저 받아 검토·승인한다.
4. **완료 조건 명시:** "무엇이 되면 끝인지"를 요청에 적는다.
5. **전 과정 기록:** 프롬프트, 결과, 문제점, 개선 내용을 기록한다.

### 8-2. 설계안 작성 규칙 (CLAUDE.md에 명시)

기능 구현을 요청하면 Claude Code가 다음 순서를 따르도록 한다.

1. **세부 항목 분해:** UI, 데이터 검증, DB 쿼리, 권한, 예외 처리 등으로 잘게 나눈다.
2. **선택지 비교:** 항목마다 가능한 구현 방법을 장단점 표로 비교한다.
3. **선택과 이유:** 프로젝트 조건에 비추어 하나를 고르고 이유를 설명한다. 판단이 필요한 항목은 "결정 필요"로 표시한다.
4. **구현 방식:** 만들 파일, 구현 순서, 예상 문제와 대응 방법을 정리한다.
5. **승인 대기:** 승인하거나 수정 사항을 줄 때까지 구현하지 않는다.
6. **구현 후 보고:** 완료 조건 충족 여부, 설계안과 달라진 점, 남은 문제를 보고한다.

### 8-3. 프롬프트 템플릿

| 용도 | 구성 |
|---|---|
| 구현 | 기능명 + 요구사항 + 제약 + 완료 조건 + "설계안부터 보여줘" |
| 디버깅 | 현상 + 재현 순서 + 기대 결과 + 실제 결과 + 에러 로그 + 이미 시도한 것 → 원인 후보를 가능성 순으로 요청 |
| 리뷰 | 보안 / 요구사항 누락 / 버그 / 개선 4가지 관점 + 심각도 + 추측 여부 표시 (Claude·Gemini 동일 사용) |

**구현 프롬프트 예시**

```
일정 등록 기능을 구현해줘.
[요구사항] 우측 상단 버튼 → 등록 폼 / 저장 직전 같은 과목·같은 날짜 일정이 있으면 확인 창
[제약] status가 active가 아닌 사용자는 등록 불가 (화면과 서버 모두 검사)
[완료 조건] ① 등록 즉시 캘린더에 유형별 색상으로 표시 ② 중복 날짜면 기존 일정 목록 표시 ③ 승인 대기 사용자는 버튼이 안 보이고, API 직접 호출도 거부

CLAUDE.md의 작업 방식대로 설계안부터 보여줘.
```

**기록 방식:** 날짜 · 기능 · 프롬프트 버전 · 결과 · 문제점 · 개선한 점을 표로 기록하고, 승인·수정한 설계안과 AI 대화 로그를 GitHub 저장소(`docs/`, `logs/`)에 함께 보관한다.
