# AI chat log 작성 규칙

AI와의 대화를 `logs/`에 기록할 때 따르는 규칙이다. 기준 예시는 [`logs/2026.11.04_기획서작성.md`](../../logs/2026.11.04_기획서작성.md)다.

기록하는 목적은 두 가지다.
1. 나중에 어떤 대화를 했고, 어떤 과정으로 무엇을 바꿨는지 다시 보기 위해
2. 최종 발표의 프롬프트 엔지니어링 과정, 트러블슈팅, 회고 자료로 쓰기 위해

---

## 1. 파일 이름

`logs/YYYY.MM.DD_작업명.md`

- 예: `logs/2026.11.04_기획서작성.md`, `logs/2026.11.10_F1로그인.md`, `logs/2026.11.12_F4교차리뷰.md`
- 날짜는 점(`.`)으로 구분하고, 작업명은 띄어쓰기 없이 쓴다.
- 같은 날 같은 작업이 여러 번이면 끝에 `_2`, `_3`을 붙인다.
- 사용 도구는 파일 이름이 아니라 문서 상단 표에 적는다.

---

## 2. 문서 구조

문서는 아래 순서로 구성한다. 각 부분의 작성법은 3장부터 설명한다.

| 순서 | 부분 | 필수 여부 |
|---|---|---|
| 1 | 제목 | 필수 |
| 2 | 상단 정보 표 | 필수 |
| 3 | 작성 방식 인용문 | 필수 |
| 4 | 목차 | 필수 |
| 5 | 대화 기록 (주제별) | 필수 |
| 6 | 트러블슈팅 | 오류가 있었을 때만 |
| 7 | 교차 리뷰 결과 | 교차 리뷰를 했을 때만 |
| 8 | 결정 변경 이력 | 필수 |
| 9 | 최종 확정 사항 | 필수 |

각 부분 사이에는 구분선 `---`을 넣는다.

### 전체 틀

```markdown
# AI Chat Log: commitSW (작업명)

| 항목 | 내용 |
|---|---|
| 날짜 | YYYY-MM-DD |
| 단계 | (예: 구현 · F4 일정 등록) |
| 사용 도구 | (예: Claude Code (VS Code)) |
| 원문 | (공유 링크 또는 "Claude Code 세션 export 파일") |
| 결과물 | (만든 파일, 커밋, 문서) |

> 작성 방식: 사용자 메시지와 AI 응답을 모두 요약했다. 대화마다 **요청 → 응답 → 결정**으로 나눠 기록했고, 문서 끝에 결정이 어떻게 바뀌어 왔는지 [결정 변경 이력](#결정-변경-이력)과 [최종 확정 사항](#최종-확정-사항)을 정리했다.
```

## 3. 상단 정보 표

| 항목 | 쓰는 법 |
|---|---|
| 날짜 | `YYYY-MM-DD` |
| 단계 | 기획 / 구현 / 디버깅 / 리뷰 중 하나 + 관련 기능 ID (예: `구현 · F4 일정 등록`) |
| 사용 도구 | Claude (claude.ai) / Claude Code (VS Code) / Gemini Pro. 여러 개면 모두 |
| 원문 | 원문을 볼 수 있는 곳. claude.ai는 공유 링크, Claude Code는 `/export`로 저장한 파일 |
| 결과물 | 이번 대화로 만들거나 바꾼 파일, 커밋, 문서 |

---

## 4. 목차

- 번호는 두 자리로 쓴다: `01.`, `02.`, … `10.`
- 대화 주제는 본문 `## N. 제목`의 제목과 똑같이 쓴다.
- **목차의 마지막 두 줄은 반드시 앵커 링크로 쓴다.**

  ```markdown
  21. [결정 변경 이력](#결정-변경-이력)
  22. [최종 확정 사항](#최종-확정-사항)
  ```

- 트러블슈팅이나 교차 리뷰 장이 있으면 그 두 줄 바로 앞에 같은 방식으로 링크를 추가한다.

  ```markdown
  19. [트러블슈팅](#트러블슈팅)
  20. [교차 리뷰 결과](#교차-리뷰-결과)
  21. [결정 변경 이력](#결정-변경-이력)
  22. [최종 확정 사항](#최종-확정-사항)
  ```

### 앵커 링크 만드는 규칙 (GitHub 기준)
GitHub는 제목마다 자동으로 앵커를 만든다. 링크의 `#` 뒤에는 아래 규칙으로 바꾼 제목을 쓴다.

| 규칙 | 예 |
|---|---|
| 띄어쓰기는 `-`로 바꾼다 | `결정 변경 이력` → `결정-변경-이력` |
| 영문은 소문자로 바꾼다 | `AI 리뷰` → `ai-리뷰` |
| 마침표, 괄호, 쉼표 등 문장부호는 지운다 | `1. 대회 공지 숙지` → `1-대회-공지-숙지` |
| 한글은 그대로 둔다 | |

- 그래서 링크가 깨지지 않으려면 **마지막 두 장의 제목을 정확히 `## 결정 변경 이력`, `## 최종 확정 사항`으로 쓴다.** 앞에 번호를 붙이지 않는다.
- 작성 후 GitHub에서 링크를 눌러 해당 장으로 이동하는지 확인한다.

## 5. 대화 기록

### 형식
- 주제마다 `## N. 제목`으로 시작하고, 아래 세 칸을 이 순서로 쓴다.
  - `### 👤 요청`
  - `### 🤖 응답`
  - `### ✅ 결정`
- 주제와 주제 사이에는 `---`을 넣는다.
- 제목은 무엇을 했는지 드러나게 짧게 쓴다 (예: `3. 1차 결정 및 기술 스택 비교`).

### 👤 요청
- 사용자 메시지를 요약한다. 번호를 매겨 여러 개를 요청했으면 번호를 그대로 살린다.
- 짧은 원문은 그대로 인용해도 된다.
- 사용자가 직접 수정한 내용, 제안을 받고도 유지하기로 한 내용도 적는다.

### 🤖 응답
- 결론만이 아니라 **판단 근거**를 남긴다: 비교한 선택지, 고른 이유, 지적한 리스크.
- 비교표가 있었으면 표로 남긴다.
- 설계안을 받았다면 항목별 선택과 이유를 요약한다.
- 코드 전체를 붙이지 않는다. 파일 이름과 핵심 변경 내용만 적는다.

### ✅ 결정
- 이번 대화에서 **확정된 것만** 적는다.
- 결정이 없으면 `없음 (검토만)`이라고 적는다.
- 설계안을 수정해서 승인했다면 무엇을 왜 바꿨는지 적는다.

## 6. 트러블슈팅 (오류가 있었을 때만)

최종 평가에서 가장 비중이 큰 항목(프롬프팅 및 트러블슈팅 40%)의 자료다. 오류 하나당 표 하나를 쓴다.

```markdown
## 트러블슈팅

### (오류 이름)

| 항목 | 내용 |
|---|---|
| 현상 | 무엇이 어떻게 안 됐나 |
| 재현 방법 | |
| 원인 | 최종적으로 밝혀진 원인 |
| 해결 | 무엇을 바꿨나 |
| 사용한 프롬프트 | 디버깅에 쓴 프롬프트 (여러 번이면 v1 → v2 변화) |
| 배운 점 | 한 줄 |
```

## 8. 결정 변경 이력 (필수)

이번 대화에서 같은 주제의 결정이 어떻게 바뀌었는지 정리한다.

| 열 | 쓰는 법 |
|---|---|
| 주제 | 인증 방식, 프론트엔드, 일정 유형 등 |
| 변경 과정 | `A (3) → B (4) → C (5)`처럼 쓰고, 괄호에는 해당 대화 번호를 적는다 |
| 최종 결정 | 이번 대화가 끝난 시점의 결정 |
| 바뀐 이유 | 한두 줄 |

- 바뀐 결정이 없으면 표 대신 `이번 대화에서 바뀐 결정 없음`이라고 적는다. 장 자체는 지우지 않는다 (목차 링크가 깨지지 않게).
- 여기 적은 변경은 `docs/decisions.md`의 변경 이력에도 한 줄씩 추가한다.

---

## 9. 최종 확정 사항 (필수)

이번 대화가 끝난 시점에 확정된 내용을 `| 영역 | 내용 |` 표로 정리한다.

- 기획 단계처럼 결정이 많은 대화는 서비스, 인증, 일정, 기술 스택, DB 등 전체를 정리한다.
- 구현 단계는 이번에 구현한 기능과 관련된 확정 사항만 정리한다 (예: 영역 = 화면 구성, 검증 규칙, 사용한 라이브러리, 남은 문제).
- 아직 정하지 못한 것은 `미정` 영역에 모아 적는다.
