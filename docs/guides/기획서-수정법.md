# 기획서 수정 규칙

기획서(`docs/기획서.md`)를 고칠 때 따르는 규칙이다.

## 1. 수정 순서
1. 결정 자체가 바뀌는 수정이면 `docs/decisions.md`를 먼저 고치고 변경 이력을 남긴다.
2. 기획서의 해당 장을 고친다.
3. 핵심 결정이 바뀌었으면 `CLAUDE.md`의 핵심 결정 요약도 고친다.

## 2. 수정 제안 방식
- 사용자는 옵시디언에서 직접 편집한다. **요청이 없으면 파일을 직접 고치지 말고 수정안만 텍스트로 제시한다.**
- 수정안은 아래 표 형식으로, 고칠 부분만 보여준다.

  | 위치 | 현재 | 수정안 | 이유 |
  |---|---|---|---|

- "꼭 고칠 것"과 "선택 사항"을 나눠서 제시한다.
- 사용자가 유지하기로 한 표현은 다시 지적하지 않는다 (아래 4장).

## 3. 작성 규칙
- **문체:** 개조식, 문장 끝은 "~한다" 체
- **높임:** 교수님께서, 조교님 (표 안에서도 통일)
- **표 안 줄바꿈:** `<br>` 사용. PDF 변환 후 글자로 보이지 않는지 확인
- **링크 목록:** 줄마다 빈 줄을 두거나 `-` 목록으로 써서 한 문단으로 합쳐지지 않게 한다
- **장 구성:** 1. 프로젝트 개요 / 2. 문제 정의 / 3. 기존 서비스와의 차별점 / 4. 기능 요구사항 / 5. 사용자 시나리오 / 6. 데이터 설계 및 보안 / 7. AI 워크플로우 및 환경 설정 / 8. 초기 프롬프트 전략 / 9. 향후 계획

## 4. 용어 통일표

| 사용 | 사용하지 않음 |
|---|---|
| 오픈채팅방 | 단톡방 |
| 학부 명단 | 학과 명단 |
| 종일 일정 / 시각 일정 | 하루 종일 일정 |
| 소프트웨어학부 | 소웨 (보고서 본문에서는 정식 명칭) |
| 휴강 / 과제 / 시험 / 공지 | |

## 5. 최종 발표용으로 고칠 때
최종 발표 양식은 기획안 요약 / 결과물 시연 / 프롬프트 엔지니어링 과정 / 트러블슈팅 / 회고다. 기획서 전체를 고치기보다 다음을 따로 준비한다.
- 기획 요약: 1~3장을 1쪽으로 압축
- 프롬프트 개선 사례: `docs/plan.md`의 프롬프트 기록표에서 v1 → v2 비교가 뚜렷한 사례
- 트러블슈팅: `logs/`의 트러블슈팅 기록
- 회고: `docs/decisions.md`의 변경 이력에서 배운 점
